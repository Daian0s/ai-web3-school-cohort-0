## Handbook Reading — Agent Fundamentals (Completed)

### The problem an agent solves

A plain LLM (Day 2) only replies with text — it can't check a balance or read the
blockchain. It's "a brain with no hands."

**Solution: give the LLM tools and put it in a loop:**

```
OBSERVE (what's the current state?)
   ↓
DECIDE (which tool do I need?)
   ↓
ACT (call the tool)
   ↓
result → back to OBSERVE (until done)
```

### How tool calling actually works

The LLM never executes anything itself. It says "I want to call this tool with these
arguments" in a structured format (JSON). Surrounding code (the harness) actually runs
it and returns the result back into context.

**Example (Web3):**
1. LLM decides it needs `get_balance(address="0xABC...")`
2. Code makes the RPC call (Day 3) → "2.5 ETH"
3. LLM receives the result as new context → answers the user

**Key point**: the LLM only knows a tool's name, required arguments, and return shape —
not its internals. Same discipline as Day 2's structured prompting, applied to tool
definitions instead of output format: the clearer the description, the more reliably
the right tool gets called.

### Read vs. write tools — different trust levels

| | Read | Write |
|---|---|---|
| Effect | Reads data | Changes state / sends funds |
| Reversible | Yes | **No** |
| Wrong call | Just re-query | Funds can be permanently lost |
| When allowed | Freely, from day one | Only with guardrails (confirmation, spend limits, testnet first) |

Not unrelated mechanically (same tool schema) — the split is about **risk level**. This
is why the learning plan (and this project) always starts read-only.

### Target build

First agent = one read tool:
```
read_contract_info(address) → RPC (Day 3) → reads contract → LLM explains it
```
The OBSERVE→DECIDE→ACT loop wrapped around a single read-only tool.
